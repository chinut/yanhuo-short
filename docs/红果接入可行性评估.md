# 红果能不能加入？—— 基于 `G:\AI\apk-analysis` 的评估

> 目标：判断能否用那份 APK 逆向成果把**红果**接回本项目。
> 结论先行：**技术上能做到，但做不到"能全部看"，所以不值得做。**
> 下面是推理链和证据。

---

## 一、先给结论

| 问题 | 答案 |
|---|---|
| 那份分析能让我调通红果 App 接口吗？ | 能，签名算法是完整的 |
| 调通后能拿到全部集吗？ | **不能，只有前 3 集** |
| 那和现在的七猫比呢？ | 七猫是**全集**，红果是 3 集 —— 加回来是**倒退** |
| 有没有别的价值？ | 有：弹幕、更高画质、更好的封面。但都不值得引入一整套签名+CENC |
| 建议 | **不加**。若哪天只想要红果的元数据/搜索，用网页 JSON 就够，不必碰 App 签名 |

---

## 二、红果有两条通路，但**都撞同一堵墙**

`src-hongguo/native/core/` 里红果是实现得最完整的 provider 之一，两条通路：

| 通路 | 域名 | 鉴权 |
|---|---|---|
| App/API | `api5-normal-sinfonlineb.fqnovel.com`（番茄小说域名族） | `X-Gorgon` + `X-Khronos` + `X-SS-STUB`；弹幕另加 `X-Argus`/`X-Ladon` |
| Web/HTML | `hongguoduanju.com` | 无，仅 UA/Referer |

**Web 通路我已经实现过并实测过**：前 3 集 `HTTP 200`，第 4 集起 `HTTP 404`。

关键是 **App 通路也过不去**，证据有三条，互相印证：

### 证据 1：App 详情的分集**本身就只返回免费集**

`provider_hongguo_detail.go:70-113` 的解析有个强校验：

```go
total, _ := strconv.Atoi(mapString(detail, "episode_cnt"))
if len(entry.Chapters) == 0 || total > len(entry.Chapters) {
    return entry, errors.New("红果 App 未返回完整分集，已尝试其他详情入口")
}
```

这条校验的**存在本身**就说明：`episode_cnt`（总集数）**大于** `video_list`（能拿到的分集）是常态 ——
否则不需要写这个判断。上游作者加它，正是因为被打到过。

### 证据 2：官方测试用例里的集数是 **2~3**

`app_test.go:146-163`：

```go
detail := map[string]any{"series_id": "700001", "series_title": "合成测试", "episode_cnt": 2,
    "video_list": []any{ ...两集... }}
// 通过（2 集 == 2 集）
detail["episode_cnt"] = 3
// 失败："incomplete details accepted"
```

作者构造的"正常"数据就是 **2 集**，把总数改成 3 就会判失败。
这个数字和我真机实测的红果付费墙（第 1/2/3 集可播、第 4 集 404）**完全吻合**。

### 证据 3：上游自己的错误文案承认了这件事

```go
// provider_hongguo.go:230
"红果未返回所请求的剧集，可能仅允许网页试看；请在站点确认该集的访问权限"

// provider_hongguo.go:235
"红果该集未提供公开播放地址，可能需要登录或 App 授权；不会将试看集冒充该集下载"
```

第二条尤其说明问题：作者明确写了"**不会将试看集冒充该集下载**"——
即"某一集取不到就是取不到，不许拿试看集顶上"。这是**刻意不绕过付费墙**的设计选择。

### 补充：`episode_cnt` 是**服务端按权限动态给**的

`provider_hongguo.go:263` 拿它渲染 `remark`（就是界面上"共N集"那行文案）。
所以同一部剧，未授权时服务端给 `episode_cnt=3`，你连"其实有 96 集"都看不到。

> 这解释了为什么红果那条链路**不可能**通过改客户端解决：
> 不是客户端少做了校验，而是**服务端根本不下发**。

## 三、就算硬做，要付出什么代价

假设不管上面那些，仍然要接 App 通路。要移植的东西：

| 要做的事 | 难度 | 源码位置 |
|---|---|---|
| `X-Gorgon` 签名（20 字节 XOR + RotateLeft8 + Reverse8，26 字节 hex） | **中** — 算法完整，照着写就行 | `provider_hongguo_sign.go:23-47` |
| `X-Argus` / `X-Ladon`（弹幕用，含 SM3 国密） | **高** — 常量含义未明（报告 §9.3） | `provider_hongguo_comment_sign.go` |
| `spade_a` → AES-128 密钥（自定义混淆解码） | **中** — 算法完整 | `provider_hongguo_playback.go:160-201` |
| **CENC 播放**（`cenc-aes-ctr` 解密） | **很高** ← 真正的拦路虎 | 见下 |

### CENC 那一步是硬伤

上游把密钥交给播放器，靠的是 **ffmpeg 的 `decryption_key` 选项**：

```
lib/player_screen.dart:1018
    if (plan.decryptionKey.isNotEmpty)
      'decryption_key=${plan.decryptionKey}',

lib/media_library.dart:422
    input.addAll(['-decryption_key', plan.decryptionKey]);
```

这是 **mpv/ffmpeg 专有**的写法，走的是 ffmpeg 的 crypto 协议。

而我们用的是 **Media3 ExoPlayer**。ExoPlayer 的 CENC 支持要经过 `MediaDrm`，
需要 **KID + IV**（ClearKey 需要 license 响应里带 KID→Key）。
但上游解出来的**只有 16 字节密钥，没有 KID** —— 报告 §9.9 也承认：

> 红果不做 CENC 解密：Go 侧只解出 16 字节密钥…IV/`cenc` 默认常量在 Go 侧完全没有实现

也就是说：**要么换播放器内核（mpv），要么自己啃 ffmpeg 的 `crypto` 协议**。
为了 3 集，不值得。

## 四、还有个技术现实：签名很可能已经过期

- 报告里的 `X-Gorgon` 魔数与 20 字节异或密钥，是**从 2026-10-03 的 APK 里还原的**；
- 字节跳动的风控参数是按客户端版本滚动的（`X-Argus` 里那些 `6.8.1.32`、
  `v04.07.01-ml-android` 就是版本指纹）；
- 报告 §9.15 明确列了"**是否存在服务端风控/设备指纹校验无法从客户端源码判定**"。

所以即使全部移植完，也可能**打过去就被拒**，而且失败原因在服务端、我们看不到。
这是一个投入很大但**结果不可验证**的方向。

## 五、我的建议

### 不建议接（理由按重要性排序）

1. **达不到目标** —— 需求是"能全部看"，红果给 3 集，接回来是倒退；
2. **CENC 那一步要换播放器内核**，为 3 集不值；
3. **结果不可验证** —— 风控可能已变，做了也不知道成不成；
4. **有"刻意不绕过付费墙"的现成判断** —— 上游作者已经踩过并主动放弃，
   我们没有必要再踩一遍。

### 如果仍然想要红果的**部分**能力

有些东西是**不依赖付费墙**的、也确实比七猫强：

| 能力 | 可行性 | 做法 |
|---|---|---|
| 元数据补全（简介/封面/备案号） | ✅ 可行 | 网页 `/detail?series_id=` 的 JSON-LD，**不需要 App 签名** |
| 搜索 / 联想 | ✅ 可行 | 网页 `/search/{词}` 与/incent_resource/suggestion（联想走 App 域但无 body，签名简单） |
| 弹幕 | ⚠️ 要 X-Argus（SM3） | 不建议 |
| 榜单 | ✅ 可行 | 网页 `/rank/hot-real-drama`（本项目已实测过） |

也就是说：**要红果的"信息"可以，要它的"片子"不行**。
而信息层面，本项目之前那版 `HongguoSource` 已经做到了（就是因此才发现 3 集墙的）。

### 真正该做的方向

红果这条路已经确认是死的（两次逆向、两个通路、同一堵墙）。
要提高"能全部看"的覆盖率，应该去找**像七猫那样一次给全集直链**的源。
判据很简单，一句探测就能定：

```
拿一部已知集数的剧，比较「详情声明的总集数」与「play_list 里非空地址的条数」
相等 → 全集源，值得接
不等 → 有付费墙，跳过
```

本项目把这个判据写成了脚本，见 `tools/probe_qimao.py`（换成目标域名即可复用）。

## 六、后续更正：它凭什么能看全集

写这份评估时只分析了红果一条通路，漏看了整体。补上：

### 它也没有破解红果

上游 README 自己写着（第 32 行）：

> 站源可用性、清晰度和区域限制取决于源站及网络；**应用不解除源站 VIP 或其他授权限制**。

代码也印证 —— provider_huangdou_vip.go:9-77 是专门用来**标记**哪些集是 VIP 的
（is_vip / pay_type=vip / ip_episodes[] / episode.type=vip 四种判据），
**只标记，不解锁**。它的红果同理：App 通路调 ideo_model，但 episode_cnt
服务端只给 3，客户端无能为力。

### 真正的原因：它接了 21 个源

provider_duanju.go:58-71 的源表 12 个，加上红果/黄果系/DSD/韩小圈等共 **21 个**。
所以能看全集的机制是**覆盖率**：A 源要会员的那部，B 源往往免费。
不是解密，是货比三家。

### 它比我强的地方：猫果 = 七猫官方 API

provider_duanju_api.go 实现了七猫**官方 App API**：

| 能力 | 它（官方 API） | 我（xiaoqi.icofun.cn 公开接口） |
|---|---|---|
| 搜索 | pi/v1/playlet/search（带 sign） | ?name= ✓ |
| **分类浏览** | pi/v1/playlet/tag/list + 目录分页 | ✗ **没有** |
| 详情+全集 | player/api/v1/playlet/info | ?id= ✓ |

鉴权（provider_duanju_api.go:18-94）：key = d3dGiJc651gSQ8w1、
sign = MD5(参数拼接 + key)、qm-params = base64(设备 JSON) 经 65 字符表换位，
且 headers 里有一个**固定的真机指纹**。

**但它拿到的集数和我一样是全集** —— etchMaoguoDetail（:187-202）只收集
ideo_url 非空且 
umber >= 1 的条目，len(chapters)==0 才报错，
**没有 episode_cnt 相等校验**（对比红果的 provider_hongguo_detail.go:104 有）。
说明七猫官方 API 对免费剧就是给全集，和我现有接口一致。

### 结论不变，但方向更清楚了

1. **不接红果** —— 结论维持，证据更硬了（它自己也没拿到全集）；
2. **官方 API 的增量只有分类浏览** —— 对不看签名的公开接口是能力补充，但**集数不增加**；
   代价是要冒充真机指纹，收益不成比例；
3. **该做的是加源而不是加深逆向** —— 别人用 21 个源的覆盖率解决问题，
   我用 1 个源。这才是差距所在。

### 一个便宜的判据（可直接被下一个人复用）

对任意候选源，只要比较两个数就知道值不值得接：

    「详情/列表声明的总集数」  vs  「play_list 里非空地址的条数」
    相等 → 全集源，接
    不等 → 有付费墙，跳过（红果就是这一类）

## 附：这份分析的可信度

`apk-analysis` 那份工作质量很高，值得说明它可信在哪：

1. **源码 ↔ 二进制双向印证**：应用自有函数 **529/571 = 92.6%** 逐名匹配，
   未匹配的 42 个全是闭包/`init`/第三方 option，**无一是业务函数**；
2. **关键常量逐字节命中**：`X-Gorgon` 20 字节异或密钥、播放响应掩码，
   都在 `.rodata` 里找到了；
3. **Go 的 pclntab 没被 strip**：12,544/12,738 个函数名还原成功；
4. **交叉印证**：`lite` 版剔除的功能（下载/局域网/存储）与
   `AndroidManifest.xml` "只有 3 条权限、无存储权限"完全吻合。

所以上面引用的代码级结论（尤其是"3 集"那三条证据）**是可信的**，
不是"看字符串猜的"。这也让"红果接不进来"这个判断有了足够硬的基础。
